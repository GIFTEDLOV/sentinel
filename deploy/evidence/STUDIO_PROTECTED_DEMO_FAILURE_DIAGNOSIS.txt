============================================

Scope
-----

change, fee-profile regeneration, commit, or push was performed in this task.

SDK / RPC checks
----------------

temporary directory only; the repository was not modified. Its
client.getTransaction({ hash }) and full waitForTransactionReceipt call both
returned the transaction and receipt.

The requested trace call was made exactly as follows:

Studio-dev returned:

  Method not found: gen_dbg_traceTransaction

Therefore the dedicated trace fields (return_data, stdout, stderr, and
genvm_log) are not exposed by this RPC endpoint. This is an RPC capability
limitation, not an ambiguous transaction result. The full receipt contains the
same execution result for the leader and all agreeing validators and supplies

Result-code decoding
--------------------
The agreeing validator/leader receipt result is base64:

  Am91dF9vZiByZWNlaXB0IG1lc3NhZ2U=

Decoded bytes:

  02 6f 75 74 5f 6f 66 20 72 65 63 65 69 70 74 20 6d 65 73 73 61 67 65

Decoded value:

  0x02 + "out_of receipt message"

The official GenVM SDK result-code enum defines 0=Return, 1=UserError,
2=VmError, and 3=InternalError. Thus this receipt proves:

  result_code: 2 (VmError)
  return/error payload: "out_of receipt message"

The payload is not an unknown or merely truncated error. It is the VM error
for the receipt-message fee bucket running out during startup.

The current runtime startup floor is 127878000000000, while the profile
allocated 98321562500000. Exact shortfall:

  127878000000000 - 98321562500000 = 29556437500000

The current GenLayer Studio fee-policy source computes this floor from the
propose/reveal receipt startup gas and nondeterministic-output startup charge.
The GenVM executor consumes that startup charge from data bucket 0. If the
bucket cannot cover it, the executor returns the receipt-message OOM VM error
before user code begins.

Conclusion
----------
Exact root cause:

  The deployment profile's executionBudgetPerRound was below the current
  Studio-dev GenVM startup floor. The message_receipt startup charge exhausted
  fee/data bucket 0 before contract execution. This produced result code 2
  (VmError) and the exact payload "out_of receipt message".

This is confirmed as:

  - not out of ordinary EVM gas;
  - not a fee deposit/payment exhaustion (fee accounting settled and most of
    the supplied fee was refunded);
  - not an execution-budget overrun after entering contract code;
  - not a constructor exception;
  - not calldata or address decoding;
  - not a runner failure.

Recommended correction (not applied)
-------------------------------------
No contract change is required based on this evidence. The fee profile must
be regenerated or freshly estimated with current Studio-dev v0.6 tooling so
that its measured deploy execution budget covers the live startup floor and
any measured deployment work, with the tool's recommended headroom. Do not
hand-edit or blindly hardcode feeValue. A receipt-embedded simulation
recommendation reported feeValue 1150902000078911 and
executionBudgetPerRound 127878000000000 with the same distribution, but a
fresh live estimate/profile should be obtained before any future broadcast.

No retry was performed.
